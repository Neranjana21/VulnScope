# ADR-0005: Ledger v1 wire format, PostgreSQL append protocol and checkpoint rules
Status: accepted (Slice 0, Task B). Refines ADR-0003 (hash-chained ledger), does not supersede it. No contract change in `docs/io-contracts.md`: this records how its silent points are read.
Context: ADR-0003 fixes the principles (per-chain hash chain, signed external checkpoints, INSERT-only role). `io-contracts.md` leaves byte-level and failure-mode gaps. Changing anything below after data exists is a new ledger version with new golden vectors (`tests/fixtures/ledger_golden/`, authored and cross-checked with a second engine before the implementation existed).
Decisions:
- **Canonical JSON v1.** Sorted keys in Unicode code point order (JCS-like, NOT RFC 8785, which sorts by UTF-16 code unit), compact separators, raw UTF-8, control characters < 0x20 escaped (`\n \r \t \b \f`, else lowercase `\u00xx`), no Unicode normalization (NFC and NFD hash differently). Accepted: `None`, `bool`, `int` within +-(2^53-1), `str`, `list`/`tuple` (becomes a list), `dict` with `str` keys; exact types only. Floats (including NaN and Infinity), bytes, datetimes, subclasses, lone surrogates, depth > 16, more than 10 000 nodes, strings over 8 192 characters and payloads over 64 KiB are rejected before anything is walked or copied. `ts` is aware-only, converted to UTC, always `YYYY-MM-DDTHH:MM:SS.ffffffZ`, formatted by hand.
- **Hash input.** `record_hash = hex(SHA-256(ASCII(prev_hash) + canonical_json(document)))`, where the document is `{actor, chain_id, kind, payload, prev_hash, schema_version, seq, ts}`. `||` is plain concatenation of the 64 lowercase hex bytes and the canonical bytes, no separator; `prev_hash` also sits inside the document. Genesis is `hex(SHA-256("vulnscope-ledger-v1:" + chain_id))`. The reading was confirmed by the golden vectors, whose independent cross-check also pins four rejected alternatives (raw 32-byte prev, document without prev, no prefix, newline separator).
- **Grammar** (`re.fullmatch` on ASCII only): `chain_id` `(engagement|intake):[A-Za-z0-9_.-]{1,200}`, `kind` `[a-z][a-z0-9_.]{0,63}`, `actor` `[A-Za-z0-9_.:-]{1,255}`, hashes `[0-9a-f]{64}`.
- **Total sanitizer.** `append()` of every backend first runs `sanitize_payload`, which never raises, so a hostile target string can never make a decision unrecordable (rule 8). It uses exact type tests only (no user method is called), an iterative traversal, byte budgets with a per-top-level-key share (scalars such as `rule_id` and `allowed` are served first), a record of every alteration (`sanitized: true`, `sanitization`), and exact-key, case-insensitive redaction of 14 header-style keys (`authorization, proxy-authorization, cookie, set-cookie, x-api-key, password, passwd, secret, token, api_key, apikey, private_key, credential, client_secret`; the fixed string `[redacted]`, never a hash). Keys such as `secret_ref`, `token_count` and `authorization_basis` are preserved; header lists that are not keyed are not redacted, so builders must not store them. Provenance by type: only the module-private `_SanitizedPayload` skips re-sanitizing; in-process code that can build one is already inside the trust boundary. Control characters are escaped; bidi controls, U+2028 and ZWSP are stored raw (storage is byte-exact; escaping them is a render concern, rule 9).
- **Append protocol (PostgreSQL).** One connection, one `READ COMMITTED` transaction: transaction-local timeouts, `INSERT chain_heads ... ON CONFLICT DO NOTHING`, `SELECT ... FOR UPDATE`, a cross-check of the head row against `ledger_entries` (`head_diverged` fails loud), `INSERT` the entry, `UPDATE` the head. `READ COMMITTED` is load-bearing for the first-append race. `UNIQUE(chain_id, seq)` is the independent backstop. No retries (a retry could double-append), no application lock (correctness must hold across processes), a per-chain in-process gate (fairness only, 4 writers per chain). A connection lost during COMMIT is ambiguous: the entry may exist (over-record, never under-record).
- **Error sanitization.** Only an operation, a fixed code and a SQLSTATE leave the backend; never SQL, parameters or payload. The error is raised outside the `except` block (no `__context__`, no `__cause__`). Local-capturing crash tools must not be enabled on `vulnscope.ledger`.
- **Result conventions.** `truncated.first_bad_seq` is the first MISSING seq (the minimum record count is `checkpoint_seq + 1`); an anchored-hash mismatch is `bad_record` at `checkpoint.seq`, meaning "at or before"; `fork` means a duplicate seq (unreachable on PostgreSQL); a negative or non-integer seq is `bad_record`. A forged or foreign checkpoint is an exception (`CheckpointRejected`), not a result code.
- **Checkpoints.** Signed message `b"vulnscope-checkpoint-v1\n" + canonical_json({chain_id, head_hash, seq, ts})`, domain-separated from record hashes. Only a segment this call walked and verified is signed; the export sink is written before the store; rows with a bad signature are skipped and counted; no `checkpoint` entry is appended to the chain in Slice 0.
- **Signing key.** Path only, opened with `O_NOFOLLOW`, every check on the opened descriptor, owner uid, mode 0600/0400, size cap, parent directory not group/world writable, Ed25519 only, never logged. The key must live outside the database host and under a different OS user than the database owner (in the S0 dev setup a compromised app that also holds the owner role could truncate and re-sign; stated limit). Rotation: `MultiKeyVerifier` accepts several public keys.
Consequences and limits: restates ADR-0003. Tail truncation and an edited-and-rehashed tail are undetectable without a checkpoint at or beyond them; replaying an older genuine checkpoint after truncating is undetectable (only the latest anchor counts, reports must say which checkpoint was used); a superuser can rewrite everything. `ts` is writer-attested; `verify` does not check monotonicity. A request with no resolvable org writes nothing (fail closed, documented in Task D).
Alternatives rejected: raw-byte `prev_hash` concatenation, RFC 8785 (float handling and UTF-16 ordering, no new dependency), floats via `repr`, advisory locks, SERIALIZABLE, application-level locking, chain-embedded checkpoints, a full-chain verify on every checkpoint.
Revisit triggers: GR-SEC-9 (monotonic `chain_heads` trigger and DELETE-grant review, needs a migration, blocks the Slice 1 pre-gate); `UNIQUE(chain_id, seq)` on `checkpoints`; key id and rotation metadata; JCS adoption (a canonical change is ledger version 2 with new vectors).
Verification: golden vectors (stdlib and Node engines, `sha256sum`, `openssl`), mutant list in the post-gate, measured numbers recorded against R6 in the post-gate.
