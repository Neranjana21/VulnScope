# ADR-0006: API authentication, idempotency, error codes and revoke ordering
Status: proposed (owner approved D-B1, the four error codes, on 2026-11-19; N-03 YES and N-04 on condition on 2026-11-24; the rest is accepted by the owner's read of this file and of `docs/gates/task-d-design.md` "Fix round 1/2"). Not committed.
Context: `docs/io-contracts.md` is silent or ambiguous on transport-level error codes (401, 400/413/415, 405, 5xx), API-key storage, idempotency scoping and replay rules, revoke ordering, and which API events are ledger events. Task D (`api/`) must pick, and one pick is a contract change (the code enum), so this ADR exists. Pre-gate findings PD-01..PD-25 (`docs/gates/task-d-pre-review.md`) shaped the details.

## Decisions
1. Error codes (contract change, additive, `schema_version` stays 1). `ReasonCode` gains exactly four members: `UNAUTHENTICATED` (401), `INVALID_REQUEST` (400 malformed body, 405, 413, 415, and every 422 that has no contract code), `INTERNAL_ERROR` (500), `UNAVAILABLE` (503: ledger, gate, DB or timeout failure; retry-safe, not a bug). An unknown route is `NOT_FOUND` (404). `REVOKED` and `EXPIRED` (the policy `rule_id` values the Scan section already names) are carried by a separate `PolicyReasonCode` enum, so `ReasonCode` keeps the contract's list plus the four. The two enums are pinned by exact-set tests. All errors are `application/problem+json`; `detail` text comes from a closed set of constants and never from input; `instance` is the route template, not the request path.
2. API keys: `Authorization: Bearer`, SHA-256 hex of the token stored (`hashed_key`), unsalted and unpeppered. This is acceptable only because tokens are server-minted with at least 128 bits of entropy; `parse_bearer` enforces length 32..256 printable ASCII. No pepper in S0 (would need a frozen `Settings` field). `ApiKey` has no expiry column, so keys end only by revocation. Raw key, hash and header are never logged.
3. Cross-org access is always 404 `NOT_FOUND`, identical body to an unknown id, and writes nothing to either org's chain.
4. 401, 403 `FORBIDDEN_ROLE`, 404, idempotency conflicts and requests rejected before the org's intent is known (malformed body, generic 422) are NOT ledger events: only policy decisions and engagement-scope decisions are (rule 8; contract "Policy decision"). Writing them would let any caller, or any key holder, grow an immutable chain without bound. They are visible instead as structured, allowlisted log events and in-process counters (`auth_failed`, `role_denied`, `cross_org_miss`). Engagement-creation rejections that carry a contract reason code go to `intake:<org>`; generic `INVALID_REQUEST` never does. The 403 case (an authenticated key with too weak a role) is an interpretation of rule 8 that the owner is asked to confirm by reading this file. Rule 8 reading (owner 2026-11-24): 401/403/404/conflicts are not ledger events because they are unattributable and would allow cross-org ledger spam; they are recorded instead in the scrubbed application security log (SEC-6): events `auth_failed`, `role_denied`, `cross_org_miss`, `idempotency_conflict`, asserted by `test_security_events_logged_with_allowlisted_fields_only` and `test_idempotency_conflict_is_a_security_log_event_not_a_ledger_entry`.
5. Idempotency: stored key is `sha256` over a length-prefixed encoding of `(org_id, key)`; claim-then-finalize with polling, no migration. Only terminal outcomes are stored for replay: 201/202, contract-coded engagement-creation rejections, and 409 `REVOKED`/`EXPIRED`. Transient outcomes (`NOT_YET_VALID`, rate, DNS-dependent denials, 5xx, conflicts) release the claim so a retry with the same key can succeed. Key syntax `[\x21-\x7e]{1,255}`, one header only. Same key plus different body or path is 409 `IDEMPOTENCY_CONFLICT`.
6. Revoke is effect first, record second (PD-07 repair choice): the `UPDATE ... status='revoked'` and the cancellation of `pending`/`queued`/`running` scans commit in one transaction (which also inserts the single-flight claim carrying `revoked_by`), then `engagement.revoked` is appended. A single-flight claim row (in `idempotency_keys`, no migration) guarantees one entry under concurrent revokes. If the append fails the response is 503 and the engagement stays revoked; the claim is released by marking it stale (its body, and so `revoked_by`, is kept). Repair happens on three triggers, never on a safe method: a revoke retry, the next scan-creation attempt for that engagement (best effort, after the REVOKED decision is recorded), and a bounded reconciliation pass at startup. `GET /v1/engagements/{id}` is deliberately not a trigger. Until one of those runs the revoke is effective but unrecorded; a `revoke_unrecorded` log event marks it. The ledger payload is derived from the row and the claim (`revoked_at`, `reason_sha256`, `reason_len`, `revoked_by` = key id of the revoker), so every path writes the same content except `repaired` and the actor (the appender); the reason text lives only in the mutable row. Recording never depends on searching the chain: on a chain beyond the search cap, or on search timeout or read failure, the entry is appended anyway (a duplicate is tolerated, lowest seq wins). Reconciliation reaches back 7 days (1 000 rows); older unrecorded revokes are an accepted loss.
7. No DB transaction is ever held open across a ledger call (the engine pool is 5+10 and `db/session.py` is frozen). Every D transaction sets `lock_timeout` and `statement_timeout` with `SET LOCAL`.
8. `GET /v1/ledger/verify` never opens a client-supplied path: `checkpoint` in any form is 422 `INVALID_REQUEST`. The no-checkpoint limitation is conveyed by the header `X-Ledger-Limitation`, not by a new body field. Verify is bounded (record cap, deadline, concurrency cap) and returns 503 `UNAVAILABLE` beyond them.
9. Scan creation and scan status (N-04, owner-approved on condition 2026-11-24). A scan row is inserted as `pending`, the `scan.created` entry is appended, then the row becomes `queued`; a worker must never see a `queued` scan without its ledger entry. Scan status values are `pending`, `queued`, `running`, `cancelled` (additive, no migration, no CHECK constraint; no reaper for a crashed `pending` row in S0). **Every allowed transition, and nothing else:**
   - pending -> queued (scan creation, after the ledger entry exists)
   - pending -> cancelled (the `scan.created` append failed, or a revoke raced the creation)
   - queued -> running (a worker, Slice 1)
   - queued -> cancelled (revoke)
   - running -> cancelled (revoke)

   cancelled is terminal and never restartable; nothing transitions back to `pending`. The code lists the same set in `api/scan_status.py`, which is the only module that writes `scans.status`; `tests/unit/api/test_scan_status_transitions.py` rejects every other (from, to) pair, checks this list against the code, and checks that the response view accepts exactly the four statuses. **For owner confirmation:** the four status values and the `ScanStatusView` response schema (an additive subclass-like schema in `models/schemas/views.py`; the existing `ScanView.status: str` is untouched). Every creation attempt runs at least one policy decision (range-only engagements use the first range's network address as a lifecycle probe, no DNS). Creation-time and scan-time target checks use the canonical parser from `policy/` only (D-final); a CIDR is never passed through `Action.target`.
10. Ledger payload builders record the engagement authorization under the key `authorization_basis` (never `authorization`: the ledger redaction blocklist is exact-key) and end with `sanitize_payload`. Payloads carry no floats (rate limit as integer milli-rps).
11. Authentication slots (N-03, owner YES 2026-11-24). `AuthGate` has shared slots plus slots reserved for the revoke route (the protective act), so a flood of unauthenticated requests on other routes cannot block revocation. Test: revoke succeeds while every shared slot is held, and fails in the mutant without the reservation.

## Consequences and accepted residual risks (owner to accept explicitly)
- R4: a key holder can append contract-coded rejections to its own `intake:<org>` chain and decision entries for scan attempts without bound (append-only, unprunable). Body caps, target caps and not re-writing replayed rejections limit the rate, not the total. Rate limiting is S1.
- R5: no throttle on failed authentication. Bounded damage only: well-formed random tokens cost one DB lookup, admission-limited so they cannot take more than 6 of 15 pool connections and fail fast with 503. Two further slots are reserved for the revoke route so a flood on other routes cannot block revocation; a flood aimed at the revoke route itself still can, and two orgs can fill the global scan-creation cap (4): both accepted for S0. `/metrics` carries no counters (no cross-tenant aggregates). S1 adds a throttle.
- R6: ledger verify is O(n) and open to every role; bounded by record cap, deadline and concurrency caps, not eliminated. The cooperative yield of B's `verify` is UNVERIFIED (D-early tests use a double).
- R9: `idempotency_keys` grows by one row per distinct key (24 h expiry applied lazily per key) plus one revoke memo per revoked engagement; a purge job is S1.
- Orphan `engagement.created` entries are possible (append before insert); the ledger stays valid and verify returns 404 for them.
- Revoke does not stop running work in S0 (no workers); it stops new scans and cancels live ones (T10 is S1).
- Authorization is self-attested (T7); the approver and statement are recorded by hash in the ledger and in full in the row.
- The signing key (if configured) is loaded only to derive the public verifier and is not retained; S0 dev holds key and app DB role in one process (B limit).

## Rejected
Optional `code` for non-contract errors (open enum, untestable); composite primary key or a new table for idempotency (migration, GR-POST-SEC-1 queue); advisory locks or `FOR SHARE` for single-flight (hold a pool connection across a ledger call); holding the claim transaction open (pool deadlock); ledger entries for 401/403/404 (unbounded growth, cross-chain existence leak); pepper (frozen `Settings`).

## Revisit
S1 pre-gate: worker must require the `scan.created` entry and re-decide at job start (rule 4); revoke must stop running jobs (T10, D20); auth throttle; idempotency purge job; per-org verify concurrency and rate limits; GR-SEC-9 (`chain_heads`, DELETE grants).

## Addendum 2026-11-25 (D-early fix round 1, BL-DE-2)
- Revoke is naturally idempotent and IGNORES the `Idempotency-Key` header: it is neither read nor stored under the client key. Single-flight and replay for revoke come from the memo row below, not from the client key.
- The revoke memo lives in its own key space: stored key = `sha256` of `revoke-memo-v1:<len(org_id)>:<org_id>:<engagement_id>`, a preimage namespace disjoint from client keys (every client preimage starts with `idem-v1:`), so no client key can address or occupy a memo row.
- Client keys beginning `revoke-record:` or `revoke-memo-` (case-insensitive) are reserved and rejected with 422 `INVALID_REQUEST` on create routes.
- An invalid memo row (failing the recorder's validity check) is treated as corrupt and re-recorded instead of waited on.
- Admission limits (AuthGate slots, reserved slots, queue wait, DB budget) are read only in `config.py`, defaults 8 / 2 / 3.0 s / 3.0 s, measured in `docs/gates/de-early-measurements.md` (local); a shed request gets 503 with a numeric `Retry-After`.
