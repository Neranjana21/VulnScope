# ADR-0004: Table privileges are granted in Alembic migrations, deny by default, no seam
Status: accepted (Slice 0, Task 0; design `docs/gates/slice0-plan.md` 3.10.1; evidence `docs/gates/slice0-pre-grants-dryrun.md`, `slice0-grants-phaseR.md`, `slice0-grants-phaseG.md`)
Context: `infra/postgres/init-roles.sql` runs at first container boot, before Alembic creates any table, so every table-level GRANT/REVOKE placed there failed with "relation does not exist" (live-confirmed). Roles are cluster objects and can exist early; table privileges cannot.
Decision:
- `init-roles.sql` creates the roles and the dev marker only. Any GRANT, REVOKE or ALTER DEFAULT PRIVILEGES there is a defect, enforced by a static tripwire. The wrapper runs `psql` with `ON_ERROR_STOP=1` so a failing init statement aborts boot.
- Every table privilege is applied by the migration that creates the table, after the DDL and triggers, from a literal per-migration `TABLE_GRANTS` map. Each statement block is `REVOKE ALL ... FROM PUBLIC`, `REVOKE ALL ... FROM <app role>`, then one `GRANT`, so grants converge instead of accumulating and re-running is idempotent. No default privileges anywhere. The ledger tables stay SELECT+INSERT, `chain_heads` SELECT+INSERT+UPDATE, `alembic_version` nothing; those are hard-coded in the helper, so a later migration cannot loosen them.
- Deny by default: the migration fails and rolls back if it creates any relation without an explicit grant decision, if the app role is missing (before any DDL, "No DDL was applied"), or if the effective privileges after granting differ from the map (table, column, PUBLIC, grantor, ownership).
- No seam: the app role is a module constant. There is no `-x`, environment or config path to name another role. Offline `--sql` mode is refused for 0001.
- `downgrade()` does no grant work and refuses on a database without the dev-disposable marker unless the ledger is empty.
Consequences: a new table needs a deliberate grant entry or its migration fails. A third-grantor grant that `REVOKE` cannot remove is detected and fails the migration (it is not healed). Drift on a live database is detected by the independent oracle, not healed. `alembic stamp` skips the checks and fails closed (the app gets no privileges). Residual, tracked for the Slice 1 pre-gate: monotonic-only trigger on `chain_heads` and a review of DELETE grants on `engagements`, `evidence`, `findings` (GR-SEC-9). The app-startup self-check moves to Task D.
Limits: a superuser or the table owner can still disable the ledger triggers or change grants; this ADR constrains the application role, not the database owner.
